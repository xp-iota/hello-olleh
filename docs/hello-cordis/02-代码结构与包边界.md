## 2.1 仓库全貌

```
cordis/
├── packages/
│   ├── core/            ← cordis          1848 行  框架本体
│   ├── loader/          ← plugin-loader    870 行  配置树 → 插件树
│   ├── hmr/             ← plugin-hmr       440 行  代码热重载
│   ├── create/          ← create-cordis    314 行  脚手架 CLI
│   ├── include/         ← plugin-include   219 行  读 yml/json 配置文件 + patch
│   ├── timer/           ← plugin-timer     142 行  可逆定时器
│   ├── logger-console/  ← plugin-logger-console 137 行  日志输出到控制台
│   ├── utils/           ← @cordisjs/utils   42 行  共享小工具
│   └── group/           ← plugin-group       3 行  Group 再导出
├── .github/workflows/build.yml   ← 唯一的 CI 工作流
├── package.json         ← yarn 4.14.1 workspace（packages/* + external/*）
├── tsconfig{,.base,.test}.json
├── vitest.config.ts     ← 10 行，唯一在 packages/ 之外的 TS 文件
└── yakumo.yml           ← 构建编排（yakumo esbuild + tsc）
```

💡 **没有 `src/` 顶层目录，没有构建脚本目录，CI 也只有一个 workflow**（`.github/workflows/build.yml`）。整个仓库就是一个极简的 yarn workspace。

## 2.2 依赖方向

![包的依赖方向与分层](diagrams/02-package-layers.svg)

**包的依赖方向与分层** — [交互版](diagrams/02-package-layers.html)（明暗主题 / 缩放 / 关系追踪 / 导出） · [IR 源](diagrams/02-package-layers.architecture.json)

- **依赖是单向的**：core 不依赖任何 cordis 包，只有两个外部依赖 · 第 1 层直接建在 core 上，彼此不互相依赖 · 第 3 层同时依赖 loader 与 timer（仅 hmr）
- **loader 是第二个中心**：870 行，包含 EntryTree / Entry / Group / isolate · 它把配置行翻译成插件树 · include 与 group 都只是它的适配层
- **两个规模异常值**：plugin-group 只有 3 行，纯粹是个标记插件 · create-cordis 314 行是独立脚手架，不参与运行时 · hmr 440 行是唯一需要双重注入的包

💡 **`core` 反过来把 loader / include 声明为可选 peerDependency**（`packages/core/package.json` 的 `peerDependenciesMeta` 里两者都是 `optional: true`）。这是为了让 core 的类型定义能引用它们扩展的接口，同时不强制安装——**类型层面的双向、运行时的单向**。

## 2.4 四个服务的自举顺序

`Context` 构造函数（`C/context.ts:36-49`）里有一段精妙的自举：

![new Context() 的自举顺序](diagrams/02-context-bootstrap.svg)

**new Context() 的自举顺序** — [交互版](diagrams/02-context-bootstrap.html)（明暗主题 / 缩放 / 关系追踪 / 导出） · [IR 源](diagrams/02-context-bootstrap.sequence.json)

- **顺序为什么不能换**：Proxy 必须最先建立，后续所有属性访问都依赖它 · 根 Fiber 必须在服务之前，服务要挂到 Fiber 的 effect 上 · ReflectService 先于其余三个服务，因为它提供解析能力
- **根 Fiber 的特殊性**：runtime 传 null 是根 Fiber 的唯一标识 · uid 固定为 0，state 跳过 PENDING 直接 ACTIVE · 没有父 Fiber，因此不参与 epoch 依赖追踪
- **自举期的陷阱**：四个内建服务在挂载时会往根 Fiber 登记 disposer · 这些 disposer 是自举产物，不应参与 restart · 所以末尾要 _disposables.clear() 把它们丢掉

💡 **`this.fiber._disposables.clear()`（`C/context.ts:47`）是个容易忽略的细节**。四个内建服务在构造时都调了 `provide`，而 `provide` 内部是 `fiber.effect(...)`，会往根 Fiber 的 `_disposables` 里塞 disposer。如果不清空，`ctx.fiber.restart()` 会把 `reflect`/`registry`/`events`/`logger` 全拆掉。

💡 **根 Fiber 的特殊性**：`runtime === null` 时走 `C/fiber.ts:200-212` 分支——`uid = 0`、`state = ACTIVE`、`store = {}`、`epoch = ''`、`execute` 是空函数、`dispose = () => this.restart()`。也就是说**根 Fiber 永不卸载，只能重启**。

## 2.5 loader 的 7 个文件

| 文件 | 行数 | 职责 |
|---|---|---|
| `L/index.ts` | 166 | `Loader extends EntryTree`，注册 3 个 internal 钩子 |
| `L/config/entry.ts` | 173 | `Entry` = 一行配置对应一个插件实例 |
| `L/config/isolate.ts` | 169 | isolate realm 的 7 步 patch 算法 |
| `L/config/tree.ts` | 123 | `EntryTree` 抽象基类：id 解析、import |
| `L/internal.ts` | 123 | `ModuleLoader`：包装 Node 内部模块加载器 |
| `L/config/group.ts` | 88 | `EntryGroup` / `Group`（可嵌套的配置分组） |
| `L/config/utils.ts` | 28 | `evaluate` / `interpolate` / `isJsExpr` |

![配置树的四个类](diagrams/02-config-tree-classes.svg)

**配置树的四个类** — [交互版](diagrams/02-config-tree-classes.html)（明暗主题 / 缩放 / 关系追踪 / 导出） · [IR 源](diagrams/02-config-tree-classes.architecture.json)

- **两个 Symbol.for 键**：Entry 用 Symbol.for('cordis.entry')（entry.ts:35） · Group 用 Symbol.for('cordis.group')（group.ts:6） · 跨实例共享，因此可以跨包识别
- **Entry 是唯一持有 Fiber 的类**：一行配置对应一个 Fiber · get disabled (:64) 沿父链向上检查 · 父级禁用则整棵子树都不激活
- **递归靠 Entry 指回 EntryTree**：某个 Entry 的 name 是 plugin-include 时会生成子树 · id 用冒号分层，形如 main:sub:leaf · Loader 的 internal 由 ModuleLoader.fromInternal() 提供（:55）

💡 **`Entry` 与 `Fiber` 是 1:1 但概念不同**：Entry 是"配置意图"（持久，写在 yml 里），Fiber 是"运行实例"（易失，会 reload）。一个 Entry 的 fiber 可以被换掉（HMR 就是这么做的，见 [08 § 8.5](08-HMR热重载.md)），Entry 本身不变。

## 2.6 三种"树"的关系

这是 loader 最容易混淆的地方：

![三种树的区别与 id 拼接](diagrams/02-three-trees.svg)

**三种树的区别与 id 拼接** — [交互版](diagrams/02-three-trees.html)（明暗主题 / 缩放 / 关系追踪 / 导出） · [IR 源](diagrams/02-three-trees.architecture.json)

- **三者的持久化位置不同**：Loader 根树只在内存，写操作是空实现 · Include 树对应磁盘上的一个配置文件 · Group 子树寄生在父配置的某一行里 · 根树到文件树的跳转条件是某 Entry 的 name 为 plugin-include
- **Group 可以自嵌套**：一个 group 行的 config 里还能有 group 行 · 嵌套深度没有硬限制 · 每层都会在 id 上追加一段
- **混淆点在于都叫「树」**：只有 Include 树与文件一一对应 · 改配置文件影响的是 Include 树，不是根树 · 定位问题时先确认自己在哪棵树上

## 2.7 为什么核心只要 1848 行

四个原因，都能在代码里找到证据：

![core 为什么只有 1848 行](diagrams/02-why-small.svg)

**core 为什么只有 1848 行** — [交互版](diagrams/02-why-small.html)（明暗主题 / 缩放 / 关系追踪 / 导出） · [IR 源](diagrams/02-why-small.architecture.json)

- **被拆出去的能力**：定时器拆成 plugin-timer，142 行 · 日志导出拆成 plugin-logger-console，137 行 · 配置驱动拆成 plugin-loader，870 行
- **用 Symbol 换命名空间隔离**：isolate 生成新 Symbol 当存储键 · 省掉一整套 realm 注册与查找表 · 代价是调试时看不到可读的键名
- **epoch 是最省代码的一处**：把依赖身份编码成字符串，比较即判定 · 不需要拓扑排序或环检测 · 详见 03 篇 § 3.4

💡 **代价是可读性**。1848 行里塞满了 Proxy trap、原型链操作、Symbol 元编程。`utils.ts` 的 `createTraceable`（`:157`，57 行）是全框架最难读的一段——它要同时处理 `this` 归属、shadow 上下文、方法绑定、嵌套 tracker 四件事。**行数少不等于简单**。

## 2.8 测试布局

30 个 spec / 4340 行，测试行数超过实现行数。确认某个语义的准确行为时，读 spec 比读实现快——「想确认什么 → 读哪个 spec」的映射表统一见 [09 § 9.9](09-关键调用链速查.md)。

💡 **`isolate.spec.ts` 在 loader 里有 538 行，在 core 里只有 123 行**。这说明 isolate 的复杂度主要来自"配置驱动的动态 realm 切换"（loader 层），而不是隔离本身（core 层只是 Symbol 作键）。

| 项 | 值 |
|---|---|

| Lint | eslint 8.57.1 + `@cordisjs/eslint-config` |
| TS | typescript 5.9.3 |
| 特殊运行参数 | `node --expose-internals --import tsx --import @cordisjs/unyaml` |
| tsx 版本 | **`npm:@cordiverse/tsx@4.19.3-fix.3`**（自维护的 fork） |

💡 **`--expose-internals` 是硬要求**：loader 的 `ModuleLoader.fromInternal()`（`L/index.ts:55`）要访问 Node 的内部模块加载器才能实现 HMR。这也解释了 `packages/hmr/src/index.ts:81` 的那句 `throw new Error('--expose-internals is required for HMR service')`。

💡 **`@cordisjs/unyaml`** 让 `import x from './a.yml'` 直接可用——HMR 包的 i18n 文件（`hmr/src/locales/{en-US,zh-CN}.yml`）就是这么引入的。
