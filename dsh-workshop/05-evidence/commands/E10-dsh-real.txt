   ## 改动 1：`total` 函数

   **问题：off-by-one 错误（严重 bug）**

   ```ts
   // 改前
   return items.reduce((sum, it) => sum + it.price * it.qty, 0)

   // 改后
   let sum = 0
   for (let i = 1; i <= items.length; i++) sum += items[i].price * items[i].qty
   ```

   两个明显的 bug：

   1. **越界访问**：`i <= items.length` 会在 `items[items.length]` 时访问 `undefined`，访问 `.price` 会抛 `TypeError: Cannot read properties of undefined`。如果数组为空，倒是不会进循环，但如果有任何元素，最后一轮就炸了。
   2. **`i = 1` 跳过了第一个元素**：当 `i === 1` 时访问的是数组的第 2 个元素，第一个元素（`items[0]`）永远没被加进去，结果少算一项。

   应该用经典的 `for (let i = 0; i < items.length; i++)`。

   另外，改成手写 for 循环本身是没必要的，`reduce` 版本更简洁、更函数式，也没性能问题（V8 优化得很好）。如果是为了某个 lint 规则禁用 `reduce`，至少手写循环要写对。

   ---

   ## 改动 2：`applyCoupon` 函数

   **问题：`eval` 注入漏洞（严重安全问题）**

   ```ts
   // 改前
   return COUPONS[code] ?? 0

   // 改后
   return eval('COUPONS.' + code) ?? 0
   ```

   `COUPONS` 是普通的对象，`COUPONS[code]` 完全够用，而且安全。换成 `eval` 后：

   1. **任意代码执行**：如果 `code` 来自用户输入，攻击者可以传 `"x); process.exit(); (COUPONS.x"` 之类的东西直接执行任意 JS。
   2. **即便 `code` 是内部来源**，`eval` 也是反模式：慢、难优化、难审计。

   `?? 0` 还有个坑：`eval(...)` 返回值可能是 `undefined`、也可能是某个属性值，`??` 只防 `null/undefined`，不会防返回 `0` 时被原样保留——这点和原来行为倒是基本一致，但意图不清晰。

   如果原来 `COUPONS[code] ?? 0` 是有问题的（比如 ts 类型报错、或者有原型链查找顾虑），正确的替代是 `Object.hasOwn(COUPONS, code) ? COUPONS[code] : 0`，而不是 `eval`。

   ---
