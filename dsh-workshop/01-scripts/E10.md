## 01. 能写成数据的先别写成代码：把一份清单注入模型视野，再看它答得有什么不同

**旁白**

## 02. 注入清单前后的真实作答对照

**旁白**

上半屏是没有清单的一次：模型答得不差，但格式随它高兴，结论埋在中间。下半屏注入了清单：第一行是结论，然后按正确性、安全、风格排序，每条带文件和行号。两次用的是同一个模型、同一段代码。差别只来自那份带头部信息的文档，它本身不含任何可执行代码。这也是为什么把做法写成数据比写成插件更划算：能进版本库，能评审，能回滚。对照两段输出的时候，重点不是哪段写得更好，而是格式是否可预期。可预期才谈得上把结果接进流水线。

**运行命令**

```bash
cd dsh-example && npm run M10:real-demo
```

**真实输出（节选）**


## 03. 顺序很清楚：能数据化的先数据化

**旁白**

不是所有东西都得写成插件。做法、规范、流程这类知识，写成一份带头部信息的文档就挺好：能被发现、能被注入、本身不含可执行代码，运行时在步骤边界把渲染好的内容送进模型视野。要跨进程调工具，那是另一套协议的活儿；要监听事件、提供服务、真的产生副作用，才轮到带生命周期的扩展。顺序搞对了，你的插件数量会明显变少。多说一层：清单是数据，所以它能被审查、能进代码评审流程、能按版本回滚。这三件事对写成插件的做法都很难做到，这就是为什么顺序建议是先数据化。

## 04. 真通道，不是画在图上的方框

**旁白**

编排层跑 runner M10 --real。它在临时目录里同步一份技能文档，再用进程内的远程调用走一遍工具列举和调用，说明外部知识和跨进程工具都有真通道。真实模式下内核读到同步进来的正文之后作答，所以这条链是端到端通的。这两块最容易掺假——画个方框就说支持，所以这里两条都留了真实往返。外部服务本身的可用性它不承诺，那不是它能保证的事。还有一点值得强调：进程内的那次远程调用也是真往返，包括工具列举和调用两步。教学示例最容易在这里画方框充数，所以这两步都留了可跑的证据。

**对照命令**

```bash
python -m runtime.runner M10 --real
```

## 05. 清单同步了，模型的回答却没变

**旁白**

这个问题的表现是「改了没反应」。别急着怀疑模型不听话，先确认正文有没有真的进到模型可见投影里。定位办法是在投影里找那条来源为技能调用的消息，同时看待认领队列有没有被清空。如果注入发生在步骤边界之外，它就会一直排在队列里，谁也读不到。改在步骤边界注入，效果立刻出现。

**症状**

两次输出几乎一样，注入的正文没有出现在模型可见投影里。

**定位**

在模型可见投影里找那条来源为技能调用的消息，确认它是否被这一步认领。

**修改**

在步骤边界注入，并确认待认领队列在跑完一步后被清空。

## 06. 清单是纯数据，头部信息决定它何时被发现

**旁白**

代码在哪：其实不是代码，是 M10 的 assets 目录里那份清单文件。前三十行看两处：头部信息写的是「什么时候该用我」，模型靠它决定要不要读正文；正文写的是输出格式，这决定了它答成什么样。全文没有一行可执行代码，所以它能进版本库、能评审、能回滚。这一集的练习就是改它的输出格式那一段。

## 07. 给清单加一条「必须给出可执行的修法」，观察输出变化

**旁白**

练习：在清单的输出格式里加一条要求——每条问题都要带具体改法，再跑一次对照。可验证的答案是注入那一次每条末尾都出现了改法，未注入那一次仍然只描述现象。这个练习顺便说明一件事：清单是可以迭代的资产，改它不需要动一行代码。

**练习**

在 SKILL.md 的输出格式里加一条要求：每条问题都要带具体改法。

**验证命令**

```bash
cd dsh-example && npm run M10:real-demo
```

**可验证答案**

注入后的每条问题末尾都出现具体改法，而未注入那一次仍然只描述现象。
