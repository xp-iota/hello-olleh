# 第一讲：一个工具要走完的十二道关

> 页数：16；语言：中文。
> 每页“旁白”与 presentation.json 的 narration 完全一致；每条论断附可复现命令。

## 01. 从一个删文件的工具说起

**旁白**

我们从一个很小的需求开始。给 Agent 加个工具，让它删掉工作区里的临时文件。听着像写个函数就完了。可问题马上来了：这工具让哪些 Agent 看见？模型真要删，谁批准？动作在哪个进程发生，沙箱拦不拦？删完之后，结果原样塞回上下文，还是只留一句话？出了事翻哪份记录？一个删文件的需求，把注册、权限、执行、审计全牵出来了。DSH 把这些分成十二个方向，每个都能单独跑，不联网，也不用真实模型。这一讲就顺着这条线走一遍，每页留一条命令，你能停下来自己敲，看见输出再听我讲。

**复现命令**

```bash
cd dsh-example && npm run all
```

## 02. 新东西该往哪儿放，只有四种答案

**旁白**

刚才那串问题，落到代码里是四个入口。最常见的，你加的是个有名字的东西：一个工具、一条命令、一个模型适配器，注册进去，别人按名字找。第二种，你不加新东西，只想在某个时刻插一脚——看一眼，或者改一下中间结果，这靠事件。第三种，你提供能力给别人用，比如读写文件、执行命令，这叫服务，重点是谁消费它。第四种最容易忽略：做法和规范这类东西，写成数据比写成代码合适。四条路最后都汇到同一个上下文，可它们的生命周期和出错方式都不一样。选错了通常有两种下场：策略被塞进实现，或者配置写了却没人读。

**复现命令**

```bash
cd dsh-example && grep -n '四条扩展路径怎么选' README.md
```

## 03. 看得见、能调用、结果能用，是三件事

**旁白**

先说工具，也就是开头那个删文件的例子。这里想说明它不是一个函数，是一条链。函数和参数格式先注册好，然后按 Agent 收窄，谁能看见哪些。模型真的调了，才轮到执行前的判断：放行、问人、还是拒绝。有个守卫在这层守底线，前面拒了，后面不许翻案。等结果出来，执行后还能改一遍模型看到的内容，同时把原值和审计留下。所以看得见不等于能调用，能调用也不等于结果可以原样喂回去。这三件事分开，权限才说得清。而结果怎么进上下文，正好是下一个方向要管的事。

**复现命令**

```bash
cd dsh-example && npm run M01
```

## 04. 别把上下文写成一根越来越长的字符串

**旁白**

上下文最容易被写成一根越来越长的字符串，然后某天开始截断。这里换了做法。每个插件只管自己那一段，变量留到最后装配才求值，要改结构就改装配好的结果，而不是拼字符串。历史太长了，加一个检查点，把旧的那段遮起来——注意是遮起来，底下的事实一条没删。再往后是估算 token、裁剪工具结果、放不下的挪到本地。压缩从来不只是把字剪短：来源、顺序、审计、还能不能恢复，都得留着。上下文装好了，接下来才是把它发给模型。

**复现命令**

```bash
cd dsh-example && npm run M02
```

## 05. 换模型和改流，是两件事

**旁白**

换模型和改流，是两件事。前者注册一个有名字的适配器，请求发到哪儿由它决定。后者不换适配器，只是在流经过的时候看一眼，或者改一下。这两条路分开摆，因为责任真的不同。示例还顺手查了几个爱出问题的地方：块有没有先开始再有增量，有没有没人认领的碎片，最后有没有给出结束原因、用量和真正的文本。这些都对了，上层才可以完全不知道模型是哪一家的。模型答完一轮，接下来要问的是：还有没有下一轮。

**复现命令**

```bash
cd dsh-example && npm run M03
```

## 06. 想改循环，不必把循环复制一份

**旁白**

想在 Agent 循环里做点事，第一反应往往是把循环复制出来改。这里不这么干。它在循环周围留了三个口子。事件告诉你顺序：一轮、一步、一次请求、一条消息，各自什么时候发生。生命周期钩子让你在会话开始、每步之前、请求之前、准备停下来的时候插进去。还有一个收件箱，接住别人想说的话，等到明确的边界再认领。循环还是那一个。插件只能在约定好的地方看和提，所以这件事既讲得清，也收得回来。循环里发生的一切，都得留痕。

**复现命令**

```bash
cd dsh-example && npm run M04
```

## 07. 日志是发生过的事，视图是模型看见的事

**旁白**

一次会话其实有两份东西。一份是日志，只往后加，序号连着，事件冻住，谁都改不了。另一份是模型看到的那一面，它只投影系统、用户、助手、工具这些节点，跟发生过的全部事情并不相等。要遮掉旧的一段，就按序号范围换掉视图，日志一条不动。分支只能从已经闭合的那一轮往下切，存盘只是存盘，不改变意思。有了这两份，审计、回放，还有刚才那节的压缩，才站在同一个地基上。留了痕，人才好介入。

**复现命令**

```bash
cd dsh-example && npm run M05
```

## 08. 人要求做什么，和系统请求许可，是两个方向

**旁白**

人和系统之间有两个方向。一个是人主动要求：我要执行什么，用斜杠命令说，注册表直接接，不消耗模型一轮。另一个是系统反过来问：这事风险不小，我能做吗？工具在执行前返回待确认，由应答方决定放这一次还是不放。有个细节值得记住：没有应答方的时候必须拒绝，不能因为忘了配，就默认拿到了权限。再往后是结构化提问、计划模式、待办和读取反馈，让人参与的状态变成看得见的数据，而不是藏在自然语言里的暗号。人放了行，事情就真的要发生了。

**复现命令**

```bash
cd dsh-example && npm run M06
```

## 09. 做什么、谁来做、在哪做，得分开

**旁白**

到了文件和命令，就是真副作用。这里的规矩是：工具只提意图，不自己去碰系统接口。文件和命令服务负责解析，决定放前台、后台还是终端；沙箱那层再把只读、可写工作区这些策略落到进程边界上。没有实现方就稳稳地拒绝，取消信号在派发前后都算。好处很实在：测试能换后端，宿主能统一看到发生了什么，线上也不会因为某个工具绕过服务，把沙箱策略整个漏掉。一个 Agent 干不完的活儿，就得分给别人。

**复现命令**

```bash
cd dsh-example && npm run M07
```

## 10. 装上子代理，模型并不会自己去用

**旁白**

有个误会挺常见：把子代理注册表装上，模型就会自己委派了。不会。注册进去的东西只是声明能力、实现子任务怎么起、怎么跑。想让模型主动选择委派，还得给它一个看得见的工具，让它显式地调。这样资源管理和决策入口是分开的，也可以由预设决定对外露出哪几种委派方式。后面收得更紧：路由到确切的提供方和模型，沙箱、审批、约束这些差异，直接写进权限预设。分出去的活儿，可能要跑很久。

**复现命令**

```bash
cd dsh-example && npm run M08
```

## 11. 还在跑吗，和这事要干成什么，是两回事

**旁白**

长任务容易被塞进一个大对象，进程状态和业务意图混在一起。这里把它拆成两半。一半管运行：还在跑吗，增量输出怎么读，要不要等，要不要杀掉，按归属隔开。另一半管意图：目标走到哪个阶段，有没有激活，并发写的时候用版本比对挡掉过期的写入，视图从日志里折出来。再往上，工作流引擎把会阻塞的活儿隔离出去，计划从耐久日志里恢复。拆开之后，恢复、并发、出错怎么办，责任才落得下来。能力也可以从外面接进来。

**复现命令**

```bash
cd dsh-example && npm run M09
```

## 12. 能写成数据的，先别写成代码

**旁白**

不是所有东西都得写成插件。做法、规范、流程这类知识，写成一份带头部信息的文档就挺好：能被发现，能被注入，本身不含可执行代码，运行时在步骤边界把渲染好的内容送进模型视野。要跨进程调工具，那是另一套协议的活儿。要监听事件、提供服务、真的产生副作用，才轮到带生命周期的扩展。顺序其实很清楚：能数据化的先数据化，剩下的再写代码。接进来的东西，都需要配置和存放。

**复现命令**

```bash
cd dsh-example && npm run M10
```

## 13. 配置不是一个随便丢东西的口袋

**旁白**

配置不是一个随便丢东西的口袋。每个插件只拥有自己那块命名空间，格式声明在边界上给默认值、做校验，版本号让并发写入显式失败，而不是悄悄覆盖。再往外接存储、域路由、附件、文件引用、凭证状态和工作区。这里仍然是所有权说话：示例只显示凭证的状态，不读也不打印内容；那些强依赖客户端连接的上传能力，明明白白留在宿主那一侧，不为了让数字好看就硬塞进核心。这些机制本身，又靠什么撑着？

**复现命令**

```bash
cd dsh-example && npm run M11
```

## 14. 派发对了，生命周期能回收，上面才立得住

**旁白**

最后看底座。同一个事件，广播、并行、串行、短路、接力，返回什么、按什么顺序跑都不一样，模式选错，控制流就变了。定时器、监听器这些副作用都绑在纤程上，插件卸载时自动回收。依赖没齐的时候纤程就挂着，齐了才激活；同名的服务可以隔到各自的域里；配置还能按调用范围叠加。上面那些花哨的可插拔能力，全踩在这两件事上：派发是对的，生命周期是可逆的。十二个方向讲完了，看看它们怎么合到一起。

**复现命令**

```bash
cd dsh-example && npm run M12
```

## 15. 十二个方向，一个装配点

**旁白**

这张图不是画出来的愿景，是从架构产物里取出来的运行结构。十二个模块沿着那四条路进来，最后都汇到同一个装配函数。图上还留着离线和真实提供方的分叉，以及两个故意空着的接口。只有一个装配点，好处很朴素：测试怎么替、默认为什么离线、资源在哪回收、真实路径怎么切，都只需要在一个地方解释一次。下半张是刚才那条命令的真实输出，结构和行为可以放在一起验。


## 16. 回到那个删文件的工具

**旁白**

回到开头那个删文件的工具。现在你应该能一口气说出它会经过哪些地方：注册和可见性、执行前的判断、真正干活的服务和沙箱、结果怎么进上下文、日志里留下什么，以及这一切在插件卸载时怎么收回去。这一讲想留下的不是十二组接口名，而是一个习惯：拿到任何一个能力，先问它归谁。缺能力、缺实现方，就明确地拒绝，别含糊过去。下一讲我们换一个系统，同样十二个方向，看它把边界画在了哪里。

**复现命令**

```bash
cd dsh-example && npm run typecheck && npm test && npm run all
```
