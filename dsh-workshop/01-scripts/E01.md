## 01. 给 Agent 加一个 word_count 工具，让真实模型自己决定调用它

**旁白**

这一集你要做的事很具体：给 Agent 加一个数词数的工具，然后让真实模型自己决定要不要调它。命令就一条，npm run M01，现在就可以暂停敲进去。你会看到三段输出：模型发出的 word_count 调用、工具结果回灌成「7 词 / 49 字符」，最后模型用一句中文报结果。注意这里的模型是真的在跑，不是固定回复。看到这三段，说明工具从注册到回灌的整条链是通的。

**本集任务**

给 Agent 加一个 word_count 工具，让真实模型自己决定调用它；再在编排层给自有工具槽装一条可回收的处理阶段

## 02. 这条命令的真实输出

**旁白**

屏幕上是刚才那条命令的真实输出。第一行告诉你推理服务是 MiniMax，走的是真实 HTTP 加 SSE。第二行是模型可见工具，只有 word_count 一个。往下，模型发起的调用带着它自己填的参数，工具结果那一行的 isError 是 false，渲染后的内容是七词四十九字符。最后 step 数是二，因为工具调用会多出一步：一步调用，一步收尾。这个 step 数很有用，它是判断模型到底调了工具还是自己编了答案最快的办法。

**运行命令**

```bash
cd dsh-example && npm run M01
```

**真实输出（节选）**

```text
$ cd dsh-example && npm run M01
⑤ 工具结果回灌给模型:
   → isError=false · 7 词 / 49 字符
⑥ 模型最终回答: "该句共有 **7 个词、49 个字符**。"
⑦ 本轮 step 数: 2 （工具调用会多出一步：调用步 + 收尾步）
REAL_STAGE_OK M01.d kind=model provider=anthropic-compat model=MiniMax-M3 calls=2 ms=1724 in=0 out=48 finish=stop tools=word_count text="该句共有 **7 个词、49 个字符**。"
REAL_MODULE_OK M01 stages=6 calls=7 failed=0
[exit 0]
```

## 03. 看得见、能调用、结果能用，是三件事

**旁白**

工具不是一个函数，是一条链。注册那一步定下名字、参数格式和实现；restrict 决定这个 Agent 能看见哪些，看不见的工具在模型眼里根本不存在。模型真的调了，才轮到执行前的判断：放行、问人、还是拒绝。守卫在这层守底线，前面拒过的，后面不许翻案。结果出来之后还能改一遍模型看到的内容，同时把原值留在审计里。这三件事分开写，权限才说得清；写在一起，你就只能靠读代码猜某次调用为什么成功。

## 04. 同一件事，换一层：阶段有名字，拆得干净

**旁白**

换到编排层，命令是 runner M01。它补的是自己那条工具通道上的一条管线：阶段有名字，重复安装不出岔子，缺的工具会报出来，名字写错当场拒绝，拆的时候按相反顺序收干净。输出里那句 unknown stage 就是拒绝的原文。它没有去接管内核内部的工具可见性，因为那件事发生在内核里面，外面看不见也保证不了。两边的差别不是谁功能多，而是缝开在哪一层：外壳能管一次调用的内部，编排层只能管自己注册的那些槽。

**对照命令**

```bash
python -m runtime.runner M01
```

## 05. 最常见的一个坑：工具注册了，模型却看不见

**旁白**

说一个真会遇到的问题。你把工具注册了，模型却完全不提它，step 数停在一。这时候别急着改提示词，先看输出第二行的可见工具列表。如果列表是空的，问题在装配顺序：插件比 Agent 晚到，而会话开始那个事件只派发一次，晚一步就永远收不到。修法是把插件放进 createHarness 的 plugins 参数里，让它在 Agent 之前就位。这个坑的特征很明显——程序不报错，只是安静地少了一样东西。

**症状**

模型答得头头是道，但输出里「模型发起的工具调用」是空的，step 数只有 1。

**定位**

先看第二行的模型可见工具列表里有没有它；再看这个插件是不是在 agent 建立之后才装的。

**修改**

把插件放进 createHarness 的 plugins 里，让它在 agent 之前就位；会话开始事件只派发一次，晚一步就收不到。

## 06. word_count 的三件套写在同一个文件里

**旁白**

代码在哪：打开 M01 的 steps 目录里那个 word-count 文件，从第二十行往下看。三件套挤在一起，正好方便对照：parameters 是模型看到的参数格式，写错了模型就传不对；output 的 schema 是规范返回值，它进审计；render 决定这个结果回灌成什么文本，那才是模型真正读到的东西。很多人只改 execute 就以为改完了，其实模型看到的是 render 的输出。iota 那边对应的是 lesson 里的 ToolPipeline 那几行。

## 07. 把 word_count 改成拒绝空文本，并让模型看到拒绝原因

**旁白**

留一个练习。打开 steps 里的 word-count，在 execute 开头加一句：文本去掉空白后为空就抛错。然后先跑离线的 M01，再跑真实的 M01。可验证的答案是这样的：离线那次工具结果的 isError 变成 true，渲染内容以 Error 开头；真实那次模型会拿着这个错误重新组织一句话。两次都对，说明你已经能控制「工具失败以什么形态回到模型面前」这件事了。

**练习**

在 steps/01-word-count.ts 的 execute 里，text 去空白后为空就抛错。

**验证命令**

```bash
cd dsh-example && npm run M01 && npm run M01
```

**可验证答案**

离线阶段的 isError 变成 true，渲染内容以 Error: 开头；真实模式下模型会重新组织一句话解释失败原因。
