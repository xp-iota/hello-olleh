## 02. 生命周期事件与一次引导

**旁白**

输出里带方括号前缀的那些行都是插件打的，它只是订阅者，不是主循环。注意 turn-stopping 那一行：插件在这里反对停止，塞了一条消息进去，于是主循环重读收件箱又走了一步。下面的 step 数是从会话日志里数出来的，不是插件自己记的账——这点很重要，因为自己记账的计数器在出错时最容易骗人。最后那个引导次数是一，说明只引导了一次，没有失控。如果你想确认插件真的没有接管循环，可以把插件卸掉再跑一次：输出里少的只有那几行日志，step 数和结果都不变。这就是「只观察不接管」的可验证形式。

**运行命令**

```bash
cd dsh-example && npm run M04
```

## 03. 三个口子：事件、钩子、收件箱

**旁白**

循环周围留了三个口子。事件告诉你顺序：一轮、一步、一次请求、一条消息各自什么时候发生。生命周期钩子让你在会话开始、每步之前、请求之前、准备停下来时插进去。收件箱接住别人想说的话，等到明确的边界再认领。这里最容易搞混的是两个入口：引导落在本轮的下一步，追加落在下一轮。选错的后果不是报错，是时机差一轮，而这种问题在日志上很难看出来。

## 04. 节点边界能观察，进行中的循环不归它

**旁白**

编排层跑 runner M04 --real。它把可观察点放在自己的节点边界上：节点成功之后、节点出错时都有钩子，图运行状态可查。这一集真实模式下你能看到内核产出标准事件流，而节点钩子照样触发——两件事互不打扰。但它明确不做中途插话，因为那需要伸手进正在跑的循环，而循环在内核里面。两层都维护一套正在跑的循环，最后谁也说不清该听谁的。还有一点值得留意：节点钩子拿到的是节点结果，而不是模型的中间状态。这个区别决定了你能在编排层做什么——能做结果审计和重试，做不了逐 token 的干预。

**对照命令**

```bash
python -m runtime.runner M04 --real
```

## 05. 引导写了却没生效，或者多跑了好几步

**旁白**

这里有两个对称的错法。一个是引导写了但 step 数没变，通常是塞进了下一轮的队列，不是本轮的下一步；另一个是 step 一路涨到上限，因为每次 turn-stopping 都又引导一次，插件在跟自己拔河。定位就看会话日志里那条记录的目标队列，以及你的引导条件是不是一次性的。加一个标记位，只在第一次反对停止，就干净了。

**症状**

step 数没变，或者一路涨到上限，插件像是在自己和自己拔河。

**定位**

看会话日志里 target 是 next-step 还是 next-turn，再看引导条件有没有做一次性判断。

**修改**

引导只在第一次 turn-stopping 时发生，用一个标记位挡住后续重复引导。

## 06. 引导写在哪个钩子上，决定它什么时候生效

**旁白**

代码在哪：M04 的 steps 里那个 lifecycle steering 文件。看它把引导挂在哪个钩子上：准备停止那个边界。这一行决定了引导落在本轮的下一步，而不是下一轮。把它换成追加的那个方法，行为立刻变成下一轮才处理——两种都对，但适用场景完全不同。读这段代码时顺手记住这个对照，比背文档管用。

## 07. 让插件在第二次 turn-stopping 时也引导一次

**旁白**

练习：把那个一次性标记改成计数，允许引导两次，然后跑离线的 M04。可验证的答案是 step 数从二变成三，引导次数变成二，并且会话日志里每次引导都留下一条记录。顺手确认一下这些数字都来自日志，而不是你新加的变量——这是这一集想留下的习惯。

**练习**

把一次性标记改成计数，允许引导两次。

**验证命令**

```bash
cd dsh-example && npm run M04
```

**可验证答案**

本轮 step 数从 2 变成 3，引导次数变成 2，而会话日志里每次引导都留下一条记录。
