## 02. 命名空间、并发失败与凭证状态

**旁白**

第一段是命名空间：格式声明在边界上给默认值、做校验，越界写别人的空间会被拒绝。第二段是版本号：两次并发写入，后一次显式失败，而不是覆盖前一次。第三段是存储与按域路由，附件按内容寻址保存。第四段是凭证：只显示状态和可用的授权流程，不读也不打印内容。屏幕上任何位置都不该出现密钥，这既是安全要求，也是教学材料能公开的前提。最后那段凭证输出请特意看一眼：只有状态和可用流程，没有任何值。教学材料要公开，这一条是底线。

## 03. 配置只保存引用和策略，不保存数据本身

**旁白**

这里的做法是：配置只保存引用和策略，真实数据交给显式的后端或提供方持有。格式声明负责默认值和校验，版本号让并发出声，按域路由决定同一份接口落到哪个存储上。强依赖客户端连接的上传能力明明白白留在宿主那一侧，不为了让功能表好看就硬塞进核心。这条纪律的收益在扩容和迁移时才看得到：换存储不用改配置结构。再补一个常见反例：把数据本身塞进配置。看着省事，后果是配置文件越来越大、迁移时必须整段搬走，而且敏感内容很容易跟着进版本库。

## 04. 投影不到的地方，直接报错

**旁白**

编排层跑 runner M11 --real。它投影一份画像，往存储里写点东西，然后故意撞一次错：某个内核没有由这一层托管的配置目录，于是错误信息直接告诉你该改用它自己的命令行参数。真实模式下内核就在这份配置投影下启动并作答，所以这条边界不是纸上的。凭证和附件仍然归宿主，不往配置对象上硬加字段。能换的地方换掉，该守的边界守住。这一集的边界也很实用：如果一个内核不接受由外层托管的配置目录，正确做法是让它报错并给出该用的参数，而不是硬塞一个目录进去让它忽略。

**对照命令**

```bash
python -m runtime.runner M11 --real
```

## 05. 配置写了，插件读到的还是默认值

**旁白**

这一集最典型的坑：配置写了，读到的还是默认值，而且什么都不报。根因通常是键写在了别人的命名空间里，或者格式声明里根本没有这个字段。定位办法是把这个插件实际读到的配置整段打出来对比。修法有两半：键写对位置，并且让格式声明对不认识的字段在校验阶段就报错。第二半是为了下次能立刻发现，而不是再猜一遍。

**症状**

改了配置文件，运行时行为完全没变，也没有任何报错。

**定位**

确认写的键是不是在这个插件的命名空间下，以及格式声明里有没有这个字段。

**修改**

把键写进正确的命名空间；格式声明里不认识的字段应该在校验阶段就报错。

## 06. 命名空间和格式声明是同一处定义的

**旁白**

代码在哪：M11 的 steps 里那个 settings namespaces 文件。注意命名空间和格式声明是在同一处定义的：声明的时候就给默认值和校验。这样做的收益是运行时代码不用再判断一遍，而非法值在装配阶段就会失败。这一集的练习就是给某个字段加上范围校验，改完之后你会发现运行时那段判断可以删掉了。

## 07. 给一个配置项加上范围校验，让越界值在启动时失败

**旁白**

练习：给一个数值配置项加上最小值和最大值，然后跑离线的 M11。可验证的答案是越界值在装配阶段就抛出可读错误，合法值照常生效，而运行时代码里不需要再写一遍判断。把校验放在边界上，运行时才干净。

**练习**

在格式声明里给数值字段加最小值和最大值。

**验证命令**

```bash
cd dsh-example && npm run M11
```

**可验证答案**

越界值在装配阶段就抛出可读错误，合法值照常生效，运行时代码不需要额外判断。
