## 02. 运行句柄、目标状态与恢复

**旁白**

前半段是运行：起一个后台任务，读它的增量输出，等它结束，或者杀掉它，按归属隔开。后半段是意图：目标走到哪个阶段、有没有激活，并发写的时候用版本号比对，过期的写入被拒绝而不是覆盖。注意那条拒绝——它是并发安全的关键，缺了它，两个写入者会互相把对方的进度抹掉。最后是从日志重放出当前状态，这就是恢复。输出里那条被拒的过期写入是这一集最该记住的一行。它的价值在于把一个并发 bug 变成了一条明确的失败，而不是一次安静的覆盖。另外注意读增量输出那一段：它是按归属隔开的，别的任务读不到你的输出，这在多任务并跑时很关键。

**运行命令**

```bash
cd dsh-example && npm run M09
```

## 03. 版本号让并发出声，而不是悄悄覆盖

**旁白**

拆成两半之后责任才落得下来。运行那一半关心进程状态；意图那一半关心业务阶段，而且它的更新走追加日志加版本比对，任何过期写入都会显式失败。再往上，会阻塞的活儿被隔离到工作线程里，计划从耐久日志恢复。这套东西的价值在断点之后才体现出来：进程重启了，意图还在，进度还能接上。补一条经验：判断一个长任务实现能不能用，就看它进程重启之后还剩什么。只剩一个句柄的，重启就断；有耐久日志和版本号的，才接得上。

## 04. 这一节反过来，编排层更强

**旁白**

这一集是唯一反过来的：编排层跑 runner M09 --real，除了目标和看板，它还有图调度、任务队列、检查点和恢复。输出里能看到任务编号幂等、租约认领、确认完成，检查点里存着计划指纹、节点状态、尝试次数和序号。原因不神秘：跨节点的调度和恢复状态天生长在编排这一层，内核只负责单次运行。你要做断了能接着跑的长流程，这一层躲不开。再说一个选型上的实际结论：如果你现在只有一个 Agent，但预感半年后要拆成好几个，先别急着上编排层，先把执行归谁定清楚，将来往外套一层就行。

**对照命令**

```bash
python -m runtime.runner M09 --real
```

## 05. 两个写入者互相覆盖，进度莫名回退

**旁白**

这个 bug 的特征是「偶尔」——进度莫名往回跳，重试几次又正常了，所以很容易被当成偶发。根因通常是更新时没带版本号，或者带了但失败被忽略了。定位就看那两条时间几乎相同的更新记录。修法是更新必须带版本号，比对失败就重读再重试。让并发出声，比让它安静地覆盖好得多。

**症状**

目标阶段偶尔往回跳，日志里两条更新的时间几乎相同。

**定位**

看更新时有没有带上读到的版本号，以及失败时是不是被忽略了。

**修改**

更新必须带版本号，比对失败就重读再重试，而不是直接覆盖。

## 06. 目标更新的版本比对写在这里

**旁白**

代码在哪：M09 的 phases 里那个 goal lifecycle 文件，搜 revision。每次更新都带上读到的版本号，比对失败就显式报错。这一行是并发安全的全部秘密，也是最容易被省略的一行——省掉之后功能照常，只有并发时才出错，而且表现是进度回退，不是异常。你做任何有状态推进的东西，都值得先把这条抄上。

## 07. 用同一个任务编号提交两次，确认不会翻倍

**旁白**

练习：用同一个任务编号连续入队两次，跑离线的 M09。可验证的答案是第二次被识别为重复，队列长度不变，并且输出里有幂等提示——不是静默丢弃。区别很重要：静默丢弃和幂等在正常路径上表现一样，只有出错时才分得出来。

**练习**

**验证命令**

**可验证答案**
