**旁白**

## 03. 换模型和改流，是两件事

**旁白**

这两件事经常被混在一起写。换模型是注册一个有名字的适配器，请求发到哪儿由它决定；改流是不换适配器，只在流经过的时候看一眼或者改一下。分开摆是因为责任真的不同：前者影响可替换性，后者影响可观测性。这一集里还有个真实的细节值得记住：真实主循环会把系统提示词当成一条消息塞进消息列表，而 Anthropic 兼容接口只认顶层的 system 字段。适配器不做这个搬运，第一步就会失败。

## 04. 替换单位是整个内核，不是模型

**旁白**

编排层跑 runner M03 --real。它的替换单位是整个内核：模型调用发生在内核里面，所以要换就换一整块。这一集的真实运行就是把内核指向 MiniMax，编排层代码一行没改。同进程的内核确实能把模型调用包住；跨进程的那种只负责传输，子进程有没有理你的中间件没人验证过，于是它把这个能力声明成不支持，编译期直接拦掉。宁可现在报错，也别让人以为已经配好了。

**对照命令**

```bash
python -m runtime.runner M03 --real
```

## 05. 真实模式跑通了，模型回复却是空的

**旁白**

这个坑值得单独讲，因为它的表现最像「链路通了」。命令退出码是零，日志也有，可模型回复是空字符串，step 数停在一。定位办法是把这一轮的会话事件逐条打出来，看 assistant attempt 里那条 chunk：失败原因就写在里面，说的是 system 消息必须走顶层字段。修好之后同一条命令立刻能拿到真实文本。空回复几乎总是翻译问题，不是模型问题。

**症状**

会话里只有一条空的 assistant 消息，step 数是 1，finish 的 kind 是 error。

**定位**

把这一轮的会话事件按序打出来，看 assistant/attempt 里那条 chunk 的失败原因。

**修改**

适配器把 role=system 的消息提升到 Anthropic 顶层 system 字段，其余消息原样映射。

## 06. 适配器最容易写错的一段：system 消息的搬运

**旁白**

代码在哪：dsh-example 的 runtime 目录里那个 MiniMax 适配器，搜 splitSystem 就能定位。这一段做的事很朴素：把角色是 system 的消息挑出来，提升到顶层字段，其余消息按顺序映射。但它是整条真实链路的成败点——不搬，第一步就失败，而失败的表现是空回复而不是报错。你接任何一家兼容接口时，第一件事都该是核对消息映射，而不是先调提示词。

## 07. 让适配器对不支持的选项显式报错

**旁白**

练习是给适配器加一条 fail loud。找到 stream 里处理选项的地方，收到没有官方映射的选项就抛错，而不是默默忽略。然后跑 npm test。可验证的答案是那条断言拿到可读的错误信息。为什么值得练这个：忽略一个选项不会让程序崩，只会让你以为它生效了，而这种问题通常要到线上才暴露。

**练习**

给 stream 加一个检查：收到没有官方映射的选项就抛错，而不是忽略。

**验证命令**

```bash
cd dsh-example && npm test
```

**可验证答案**

新增的用例断言这条路径抛出可读错误；忽略选项的实现会让这条用例失败。
