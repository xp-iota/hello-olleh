## 02. 分段装配与压缩后的模型可见面

**旁白**

输出分成几段看。第一段是各插件贡献的 prompt section，顺序是稳定的，变量留到最后装配才求值。第二段是压缩：注意 surface 节点数从几个变成更少的几个，而事件日志的长度没有变。第三段是估算与裁剪，超长的工具结果被确定性地剪短，剪掉的部分挪到本地文件，还能找回来。如果你自己写压缩，最容易错的就是把日志也一起删了——那之后审计和回放就都没了。再多说一句怎么读这段输出：估算是回放日志算出来的，不是猜的，所以你换一批历史再跑，数字会跟着变。这一点让预算策略可以被测试，而不是只能靠线上观察。

**运行命令**

```bash
cd dsh-example && npm run M02
```

**真实输出（节选）**

```text
$ cd dsh-example && npm run M02
  backend: 'LocalSpillStore',
  inlineBytes: 255,
  hasLocator: true,
  isError: false
}
结论：上下文是结构化装配结果；section/variable 控制进入什么，compaction 控制历史以什么成本继续可见；meter、pruner 与 spill 把预算变成可观测且可执行的策略。
[exit 0]
```

## 03. 遮起来，不是删掉

**旁白**

这里的做法是：每个插件只管自己那一段，要改结构就改装配好的结果，而不是去拼字符串。历史太长了就加一个检查点，把旧的那段遮起来。遮的动作作用在模型可见面上，底下的事实一条没删。再往后是估算 token、裁剪工具结果、放不下的挪到本地。四件事合起来，预算才从一句口号变成可执行的策略。顺序也别搞反：先把上下文装好，再谈发给模型。

## 04. 记忆能分范围，压缩仍在内核里

**旁白**

编排层这边跑 runner M02。它的记忆服务是真的：按用户、项目、会话三种范围拼前缀，而且默认不注入，要你显式打开。这条默认关闭很值得注意——它避免了「配置写了却不知道注了什么进去」。但把提示词整体装配起来、把历史压下去，仍然在内核里整块发生，编排层看不见那个过程。所以它干脆不声明压缩这件事，输出里那句 kernel-owned 就是这个意思。诚实地不做，比假装做了更安全。顺手记一个判断标准：一个框架说自己支持压缩，你就问它压缩发生在哪一层、日志还在不在。这两个问题答不上来，那个支持大概是接口上的支持。

**对照命令**

```bash
python -m runtime.runner M02
```

## 05. 压缩生效了，可模型答得越来越离谱

**旁白**

换个角度讲个更隐蔽的问题。压缩明明生效了，模型却开始重复问已经答过的事。这不是模型变笨，是你遮掉了还在被引用的事实。定位办法很直接：把压缩前后的模型可见面打出来对比，看少了什么。修法是遮蔽区间从检查点之后取，并且让摘要占住被遮区间的原位置，顺序信息不能丢。位置错了，模型读到的因果关系就是错的。

**症状**

压缩之后模型开始重复问已经回答过的事，或者忘掉刚确认的结论。

**定位**

对比压缩前后的模型可见面：看被遮掉的区间里是不是包含了还在被引用的关键事实。

**修改**

遮蔽区间从检查点之后取，并把摘要放在被遮区间的原位置，保证顺序信息不丢。

## 06. 压缩提供方只做一件事：换可见面

**旁白**

代码在哪：M02 的 steps 里那个 compaction provider，前四十行就够。注意它只提交一条带替换区间的事件，没有任何删除动作。这就是「遮起来不是删掉」在代码里的样子。你自己写压缩策略时可以照抄这个形状：算出要遮的区间，产出一条摘要，剩下的交给会话层。判断有没有写对，看日志长度前后是不是一致。

## 07. 把裁剪阈值调小一半，观察哪些结果被挪走

**旁白**

练习是调一个阈值。把 spill 那一段的 maxInlineBytes 从 256 改成 128，再跑一次 M02。可验证的答案是：被判定为超长的结果变多了，挪到本地文件的条数增加，但模型可见面里仍然留着能定位回去的引用。如果引用也一起没了，那就不是压缩，是丢数据。

**练习**

把 spill 阶段的 maxInlineBytes 从 256 改成 128。

**验证命令**

```bash
cd dsh-example && npm run M02
```

**可验证答案**

更多工具结果被判定为超长，输出里挪到本地文件的条数增加，而模型可见面里仍能看到可定位的引用。
